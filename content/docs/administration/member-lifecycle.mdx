---
title: 用户管理
description: 在使用本地身份的 v0.1 中，新增用户、调整用户组、修改密码和停用账号。
---

v0.1 使用 YAML 管理用户目录，不提供公开注册或 Web 创建账号。管理员通过同一份配置新增用户、调整用户组、修改密码或停用账号；每个用户应使用独立 subject，避免多人共享同一个 ByteHop 身份。

## 新增用户

1. 为用户创建独立 subject，不共用账号；
2. 在可信终端为初始随机密码生成不可逆哈希；
3. 只加入完成工作所需的组；
4. 检查组对应的 Resource 与最大 TTL；
5. 校验配置并热更新；
6. 让用户按[第一次使用](/docs/quickstart)登录并验证可见 Resource；
7. 同时验证一个不应可见的 Resource。

```yaml
auth:
  provider: local
  local:
    users:
      "alice@example.com":
        password_hash: "$2a$12$..."
        groups: [data]
        admin: false
```

`password_hash` 的完整值由管理员在可信终端生成，不要让 Agent 接收明文密码：

```bash
read -s BYTEHOP_NEW_PASSWORD
printf '%s' "$BYTEHOP_NEW_PASSWORD" | bytehop hash-password --password-stdin
unset BYTEHOP_NEW_PASSWORD
```

把输出粘贴到 YAML 后，运行 `config check`、`config diff` 和 `config reload`。新增用户不重启 Server，也不影响其他用户的 Session。

## 把账号交给用户

管理员应分别提供 Server 地址、用户名、初始密码和已授权 Resource。密码通过团队已有的 Secret 渠道交付，不要与上游数据库凭证一起发送，也不要把 `.env` 或完整配置文件交给成员。

用户拿到账号后从[第一次使用](/docs/quickstart)开始：先登录 Web 确认 Resource，需要终端或 AI 时再安装 Client。ByteHop 账号同时用于 Web 和 CLI，但两端各自建立 Session。

## 调整组或角色

先用 `bytehop config diff` 查看影响，再应用完整配置。组收紧会撤销不再满足 policy 的活动 Lease。`admin` 只改变控制面权限；它不授予任何 Resource。

需要临时扩大访问范围时，优先增加一个有明确结束时间的组变更和较短 `max_ttl`，并在任务结束后删除。ByteHop 当前不会自动让用户组关系到期，因此这项配置变化仍需由现有变更流程跟踪。

## 修改密码

重新运行 `bytehop hash-password --password-stdin`，用新输出替换该用户的 `password_hash`，再热更新。密码变化会使该用户已有 Session 与 Lease 失效，用户需要重新登录；其他用户不受影响。

不要通过聊天发送真实密码。初始密码仍通过现有的 Secret 渠道交付，并要求用户只在可信终端输入。密码哈希不能还原出明文，但仍应把部署配置作为敏感文件管理。

## 停用或移除用户

从 YAML 删除用户并 reload。ByteHop 会禁用对应 identity，并撤销其活动 Session 与 Lease；同名用户以后重新加入时，旧 token 不会恢复。

账号停用检查清单：

- [ ] 从 YAML 用户目录删除 subject；
- [ ] 预览并应用 reload；
- [ ] 在 **Sessions** 确认无活动 Lease / Operation；
- [ ] 轮换该用户可能在 ByteHop 之外接触过的 secret；
- [ ] 检查近期 Event，保留 request ID 作为交接记录；
- [ ] 以服务端 Session 与 Lease 的状态作为停用是否完成的依据。
