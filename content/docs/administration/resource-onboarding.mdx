---
title: 接入 Resource
description: 从最小权限上游身份开始，把一个数据库或内部 API 安全接入 ByteHop。
---

接入 Resource 的顺序应是“先定义用途和数据范围，再配置网关”，不要先把管理员凭证填进 YAML。完成后，获准用户只需要 Resource 名称即可通过 ByteHop 调用；上游地址和固定凭证不会进入客户端配置。

## 可以交给 ByteHop Skill

安装 [ByteHop Skill](/docs/using/agent-workflow#配置模式) 后，把下面的信息交给 Agent：Resource 用途、真实上游、固定最小权限身份、Secret 环境变量名、允许的用户或组，以及 Lease 上限。Agent 会生成最小 YAML 并调用 CLI 校验，但不会替你决定上游应授予哪些权限。

```text
请使用 ByteHop Skill 接入这个 Resource。先检查现有 bytehop.yaml，
列出仍缺少的上游、凭证引用和 Access 信息；信息齐全后再修改。
运行 config check 并展示 diff，不要直接应用。
```

## 1. 定义最小能力

先写清楚：

- 哪个团队任务需要它；
- 允许读哪些数据库、表、索引、集合或业务对象；
- 是否真的需要写操作；
- 预期最长查询时间、结果规模和并发；
- 允许哪些用户或用户组；
- 哪个系统负责最终授权。

如果一段描述里出现两种明显不同的数据范围，拆成两个 Resource。

## 2. 创建固定上游身份

在上游系统创建专用身份，不复用个人账号，也不给 ByteHop 创建用户或管理员权限。

| 类型 | 优先落实 |
| --- | --- |
| ClickHouse | database / table grant、readonly、超时、内存、并发、Quota |
| Elasticsearch | 精确 index pattern 与只读 index privilege，避免宽 cluster privilege |
| MongoDB Bridge | Bridge 专用 token；Mongo 用户固定 database / collection 与只读角色 |
| HTTP API | 专用 service account / token，只允许目标租户和业务动作 |

针对每种协议的配置示例见 [ClickHouse](/docs/resources/clickhouse)、[Elasticsearch](/docs/resources/elasticsearch)和[HTTP API 与 Bridge](/docs/resources/http-bridge)。

## 3. 添加 Resource

```yaml
resources:
  analytics:
    description: "Production analytics, read only"
    kind: clickhouse
    upstream: "https://clickhouse.internal:8443"
    credential:
      basic:
        username: bytehop_ro
        password: "${CLICKHOUSE_READONLY_PASSWORD}"
    tls:
      ca_file: "./certs/internal-ca.pem"
      server_name: "clickhouse.internal"
```

Resource 名是 Agent 会使用的稳定标识。描述应说明用途和范围，例如“订单汇总，只读”，不要只写“生产库”。

## 4. 添加最小 Access policy

```yaml
access:
  - subjects: ["group:data"]
    resources: [analytics]
    max_ttl: 15m
```

先授权给小范围试用组。管理员不会自动绕过这条 policy；若管理员也要真实查询，必须显式授权。

## 5. 检查、预览与应用

```bash
bytehop config check --config /etc/bytehop/bytehop.yaml
bytehop config diff
bytehop config reload
```

如果 diff 显示 `restart_required`，不要尝试部分应用。按[安全热重载](/docs/administration/reload)处理。

如果由 Agent 操作，先让它解释 diff 对 Session、Lease 和重启的影响；只有你明确要求应用时才执行 `config reload`。

## 6. 验收正反两条路径

- 目标用户能在 `bytehop resources` 中发现 Resource；
- 未授权用户不能发现它，也不能创建 Lease；
- 一个其他 Resource 的 Lease 不能调用它；
- 固定身份在上游确实无法越界读写；
- CLI / Web / Event 中不出现上游 credential；
- 对 ClickHouse，长查询观察与停止结果符合上游账号权限；
- 对 HTTP Bridge，越界 method、collection、projection 或 limit 在 Bridge / 上游被拒绝。

最后保留 `request_id`、可选 `query_id` 和脱敏后的验收记录。
