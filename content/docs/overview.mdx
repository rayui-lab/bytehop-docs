---
title: ByteHop 是什么
description: 快速理解 ByteHop 解决的问题、工作方式和核心设计。
---

ByteHop 是一个**面向 AI Agent 的自托管临时访问网关**。它位于 Agent 与生产数据或内部 HTTP API 之间，把长期固定凭证转成短期、可撤销、绑定资源的访问能力。

## 它解决什么

小团队常见的现状是：ClickHouse 密码写在每个人的 Agent 配置里，MongoDB 连接串被贴进对话，内部 API 的 Cookie 放在本地脚本中。这样虽然马上能用，但很难回答：谁现在还能访问、能访问什么、凭证是否已经复制、刚才实际执行了什么。

ByteHop 把问题收敛成四步：

1. 管理员在数据库或 API 侧创建固定的最小权限身份；
2. ByteHop 在服务端集中保管凭证，用户和 Agent 无需接触；
3. 已登录用户按权限为一个 Resource 申请短期 Lease；
4. 请求通过网关执行，并记录资源、身份、状态和可用的操作摘要。

## 为什么选择 HTTP

ClickHouse 和 Elasticsearch 已有成熟 HTTP API，内部服务天然使用 HTTP；MongoDB、CLI 或脚本也可以通过受限 Bridge 暴露少量明确操作。

统一使用 HTTP 后，`curl`、ByteHop CLI、Codex、Claude 和现有脚本可以使用同一套发现、授权与调用流程。团队新增 Resource 时，也不需要为每个 Agent 单独分发连接方式和真实凭证。

## 核心设计

- **凭证集中保管**：上游固定身份只存在于服务端；
- **Resource 明确能力**：一个名称对应一种用途、一组上游权限和可选契约；
- **Lease 控制时效**：每次访问绑定用户、Resource 与过期时间，可随时撤销；
- **上游落实数据权限**：数据库和 API 继续负责表、索引、集合、业务动作与配额；
- **Agent 按需发现**：先列出可用 Resource，再读取单个 contract，减少上下文占用；
- **调用可追踪**：用 actor、Agent ID、Task ID、request ID 和 query ID 关联一次工作。

## 适合怎样开始

小团队可以先接入一个高频只读场景，例如 ClickHouse 指标查询或内部订单 API。验证凭证不下发、成员权限、短期 Lease、Event 和停止长查询后，再逐个增加 Resource。

普通成员从[第一次使用](./quickstart)开始；管理员从[安装 ByteHop](./administration/installation)和[接入 Resource](./administration/resource-onboarding)开始。
