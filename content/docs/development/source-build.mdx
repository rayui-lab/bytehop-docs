这一节面向 ByteHop 的维护者。使用已经部署好的实例时，从[第一次使用](/docs/quickstart)开始即可。

## 环境要求

- Go 1.26；
- Bun 1.4；
- 运行集成验收时还需要 Docker 与 Docker Compose。

## 构建

在源码根目录运行：

```bash
make build
./bin/bytehop version
```

`make build` 先构建 Web UI，再将静态资源嵌入同一个 Go 二进制。`bin/bytehop` 同时包含服务端和 CLI。

SQLite 使用 [`cznic/sqlite`](https://gitlab.com/cznic/sqlite) 的官方 module 路径 `modernc.org/sqlite`。这个驱动不依赖 CGo，因此发布脚本可以从同一个 Runner 交叉编译六个目标平台。

## 基础检查

```bash
make check
make docs-build
```

如果只改 Go 代码或 Web UI，也可以分别运行：

```bash
go test ./...
go vet ./...
(cd web && bun run typecheck && bun run build)
```

## 版本化分发

仓库的 `.github/workflows/release.yml` 在推送语义版本 tag（例如 `v0.1.0`）时自动完成：

1. Go 测试与 Web UI 构建并行执行，Web 产物只生成一次；
2. 在原生 amd64 与 arm64 runner 上并行打包 Linux、macOS、Windows 二进制；
3. 打包生产 Compose 示例与 `bytehop.skill`，并生成 `SHA256SUMS`；
4. 发布二进制、部署包和 Skill 到源码仓库 Release，并同步到公开 `bytehop-dist` Release；
5. 从已打包的 Linux 二进制组装多架构镜像，不在 Docker 内重复测试或编译；
6. 生成 SBOM 和 provenance。

同步公开分发仓库前，维护者需要创建只授权 `rayui-lab/bytehop-dist`、仅有 **Contents: Read and write** 权限的 fine-grained personal access token，并保存为源码仓库的 Actions secret `BYTEHOP_DIST_TOKEN`。不要把个人日常使用的宽权限 token 放进 Release workflow。

本地可以预演同一打包脚本：

```bash
make release-snapshot
```

## 发布第一个版本

先确认 `main` 已通过检查并推送，再创建带说明的 tag：

```bash
git switch main
git pull --ff-only
make check
git tag -a v0.1.0 -m "ByteHop v0.1.0"
git push origin main
git push origin v0.1.0
```

推送 tag 后，GitHub Actions 会同时生成 Release 附件和 GHCR 多架构镜像。可以用 GitHub CLI 查看进度与结果：

```bash
gh run list --workflow Release
gh release view v0.1.0
docker buildx imagetools inspect ghcr.io/rayui-lab/bytehop-dist:0.1.0
```

公开分发镜像可以匿名拉取。源码仓库的镜像保持原有发布路径；正式版本 tag 不包含后缀，`v0.1.0-rc.1` 这类 tag 会作为预发布版本。

发布版本通过 Go linker flags 写入二进制，因此 `bytehop version`、`/healthz` 和管理界面显示同一个版本。

完成本地构建后，继续运行[本地验收环境](/docs/development/local-stack)。
