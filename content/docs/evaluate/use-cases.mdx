---
title: 适用场景
description: 用具体案例理解 ByteHop 如何接入数据库、内部 API 和 Agent 工作流。
---

ByteHop 的价值不在“能代理 HTTP”，而在把原本散落的长期凭证替换成可归属、短期、资源绑定的访问。

## 场景一：Agent 排查 ClickHouse 指标

**原来的做法**：把生产只读账号写入每位工程师的 Codex / Claude 配置。密码轮换需要逐台更新；长查询卡住时不知道是谁发起的。

**使用 ByteHop**：数据库管理员创建 `analytics_ro`，在 ClickHouse 侧限制库表、只读、执行时间和内存。工程师登录 ByteHop 后让 Agent 发现 `analytics`，每次查询自动领取短期 Lease。管理员可用 request/query ID 找到运行中的 SQL并停止单次请求。

**权限方式**：ClickHouse 继续负责表、只读、执行时间和内存配额，ByteHop 负责成员、Lease 和调用记录。

## 场景二：运营 Agent 查询 MongoDB 用户资料

**原来的做法**：把 `mongodb://ops:...` 连接串发给同事，Agent 获得了数据库、账号与网络位置，并可能执行超出实际任务的查询。

**使用 ByteHop**：在 MongoDB 附近部署一个 Bridge，只开放 `POST /v1/find`，限制 `users` collection、projection、limit 和 timeout。ByteHop 再为 Bridge 提供临时资源授权。Agent 不接触 Mongo URI，也不能调用 Bridge 未提供的操作。

**接入方式**：Bridge 维护少量明确的领域接口，使 Agent 只接触完成任务所需的操作。

## 场景三：替代分散的内部 HTTP CLI 凭证

团队已有一个脚本调用内部 API，但每台电脑都保存 Basic password 和 `tide_sid` Cookie。将该 HTTP client 定义成 `kind: http` Resource 后，凭证只在 ByteHop 服务端配置，Agent 用 `connect` 临时运行原脚本：

```bash
bytehop connect davinci-stage --ttl 5m -- \
  ./existing-client --base-url "$BYTEHOP_ENDPOINT"
```

这样不必立即重写现有 client，也能统一身份和 Event。若脚本能读取环境变量即可接入。

## 场景四：小团队统一 AI 的生产访问

团队需要覆盖两个数据库 HTTP API 与三条内部只读 API。ByteHop 用单二进制、YAML 和 SQLite 统一 Resource、成员权限、Lease 与 Event，适合从一个高频只读场景开始逐步接入。

## 可组合的系统

- 原生 PostgreSQL / MySQL / MongoDB 客户端可以继续使用现有数据库访问方案；
- SSH、RDP、Kubernetes 与桌面客户端可由现有堡垒机或访问平台管理；
- ByteHop 聚焦 Agent 使用的 HTTP Resource，并可与上述系统同时部署。

<Callout title="可复现的案例">
  ClickHouse、Elasticsearch、MongoDB Bridge 和 Davinci 风格 API 都在仓库 Compose 中配有确定性数据与 smoke test，可用于本地验收完整链路。
</Callout>
