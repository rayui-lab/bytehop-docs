---
title: 在 Hermes 与飞书中使用
description: 在飞书里直接描述数据任务，并在 ByteHop Event 中确认 Agent、会话和消息来源。
---

Hermes 使用现有 ByteHop Skill 和 CLI，不需要单独的 Hermes Skill，也不需要修改 Gateway YAML。用户在飞书中描述任务，Hermes 调用普通 `bytehop` 命令；CLI 会把当前会话来源关联到这次访问。

## 开始前

运行 Hermes 的机器需要：

- 已安装 ByteHop CLI，`bytehop version` 可以运行；
- 已使用实际操作者的 ByteHop 身份登录；
- 该身份至少可以访问一个 Resource；
- Hermes 的工具进程可以直接调用 `bytehop`。

ByteHop 登录身份决定权限。Hermes 会话和飞书用户只用于定位调用，不会扩大这个身份可以访问的 Resource。

## 1. 安装同一个 ByteHop Skill

Hermes 可以从 GitHub 仓库安装包含引用文件的 Skill：

```bash
hermes skills install rayui-lab/bytehop/skills/bytehop
```

安装后开始一个新的 Hermes 会话。也可以运行 `hermes skills list`，确认列表中存在 `bytehop`。安装、检查和更新均由 [Hermes Skills](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/skills.md) 自己管理，不需要另一份 ByteHop 安装器。

## 2. 在飞书中直接描述结果

不需要把 CLI 命令发给用户。直接在飞书中告诉 Hermes 想得到什么：

```text
请使用 ByteHop 查询 analytics 中最近一小时各服务的事件数量，
按事件数从高到低排列，最多返回 20 行，并保留 request_id。
```

ByteHop Skill 会让 Hermes：

1. 发现当前 ByteHop 身份可以使用的 Resource；
2. 读取 `analytics` 当前提供的调用说明；
3. 选择 `request` 或 `connect`；
4. 执行查询并返回结果；
5. 在回答中保留 `request_id`，ClickHouse 同时保留 `query_id`。

Hermes 最终仍然执行普通命令，例如：

```bash
printf '%s' 'SELECT service, count() FROM events GROUP BY service LIMIT 20' |
  bytehop request analytics POST / --body @- --content-type text/plain --json
```

命令不需要来源参数。不要让 Agent 手工复制或编造 Hermes Session ID。

## 3. 确认这次调用

查询完成后保留 Agent 返回的 `request_id`：

1. 普通用户打开 ByteHop 的 **My activity**，管理员打开 **Events**；
2. 在搜索框粘贴 `request_id`；
3. 打开最新 Event；
4. 确认 **Actor** 是实际登录的 ByteHop 用户；
5. 确认 **Agent** 是 `hermes`，**Task ID** 非空；
6. 飞书请求还应显示 **Source platform** 为 `feishu` 和对应的 **Source user**。

搜索会在服务端查询全部历史 Event，也可以直接输入 Hermes Session ID、飞书用户 ID、Agent、SQL、`query_id` 或 Resource。复制某条 Event 的 Task ID 再搜索，可以查看同一 Hermes 会话中的其他 ByteHop 调用。

## 自动关联了什么

CLI 只有检测到当前工具进程的 `HERMES_SESSION_ID` 时才启用 Hermes 适配：

| Event 字段 | 自动来源 |
| --- | --- |
| `agent_id` | 默认 `hermes` |
| `task_id` | `HERMES_SESSION_ID` |
| `source_platform` | `HERMES_SESSION_PLATFORM`，例如 `feishu` |
| `source_user_id` | `HERMES_SESSION_USER_ID` |

`request` 每次创建独立 Lease，`connect` 每个子进程创建独立 Lease。来源信息在创建时确定，随后由 Operation 和 Event 继承，不会被数据请求覆盖。

多个 Hermes 实例需要区分时，可以在各实例的启动环境设置不同的 `BYTEHOP_AGENT_ID`。通用 `BYTEHOP_*` 关联字段优先于 Hermes 自动值。

## 找不到来源信息

### Hermes 没有使用 ByteHop

运行 `hermes skills list` 确认 `bytehop` 已安装，并开始新的会话。然后明确说“请使用 ByteHop”，不要给 Hermes 数据库密码或连接串作为退路。

### Event 有结果，但 Agent 或 Task ID 为空

确认 `bytehop` 是由当前 Hermes 工具子进程直接执行的，没有经过会清空环境的中间脚本。检查工具进程是否提供 `HERMES_SESSION_ID`，但不要把它的值写入日志或手工复制到另一条会话。

### Actor 不是预期用户

Hermes 来源不会替代 ByteHop 登录。请在运行 Hermes 的机器上退出错误 Session，再由实际操作者在可信终端完成 `bytehop login`。

### 有 Task ID，但没有飞书用户

这表示 Hermes 提供了会话信息，但当前消息入口没有提供平台或用户字段。调用仍可按 Actor、Agent、Task ID 和 `request_id` 定位；不要沿用上一条消息的飞书用户。

## 记录内容

ByteHop 不读取 Hermes 对话正文。Event 保存 Actor、Agent、Task、来源平台、来源用户、Resource、请求结果和可用的 SQL 摘要；不保存通用请求体、响应体、上游凭证或 Hermes Session 的聊天内容。

`source_user_id` 是客户端上报的关联信息，不是经过 ByteHop 验证的登录身份。它可能是稳定的平台用户标识，应限制 Event 查看权限并制定保留周期。
